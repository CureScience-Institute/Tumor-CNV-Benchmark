
# Tumor-CNV-Benchmark

A GRCh38-based bioinformatics framework for benchmarking tumor purity, ploidy, and copy-number alterations (CNAs/CNVs) across multiple computational tools, including **ASCAT, FACETS, Sequenza, and PURPLE**, with comparative validation against **BostonGene (BG) clinical reports**.

The project focuses on matched tumor–normal whole-exome sequencing (WES) data and investigates how different computational approaches affect tumor purity estimation, ploidy inference, allele-specific copy-number profiles, chromosome-arm alterations, and gene-level CNV identification.

A specific objective is to evaluate **ASCAT with and without externally supplied purity/ploidy (2P) inputs**, alongside independent estimates from FACETS, Sequenza, and PURPLE.

All analyses are designed to reuse existing **nf-core/sarek GRCh38 alignment outputs**, avoiding unnecessary FASTQ realignment.

**Project status (2026-10-15): Ongoing.** Sarek alignment and initial ASCAT workflows are available. A 20-patient direct PURPLE pipeline has been launched. The complete multi-tool benchmarking and BostonGene concordance analyses remain in progress.

---

## Project Objectives

The main objectives are:

1. Compare tumor purity estimates generated by ASCAT, FACETS, Sequenza, and PURPLE.
2. Compare tumor ploidy estimates across the four computational methods.
3. Investigate differences between ASCAT with supplied purity/ploidy parameters (2P) and ASCAT with automatic parameter estimation (no-2P).
4. Evaluate the reproducibility of chromosome-arm-level copy-number gains and losses.
5. Compare focal amplifications, deletions, and gene-level CNV events.
6. Assess agreement between computational CNV predictions and BostonGene clinical reports.
7. Identify factors contributing to inter-tool discrepancies, including tumor purity, sequencing coverage, model assumptions, and WES normalization.
8. Establish a standardized framework for evaluating tumor purity, ploidy, and copy-number inference methods.

BostonGene reports are treated as an external clinical comparison reference, rather than an assumed biological ground truth.

| Tool | Primary function | Major outputs |

## ASCAT: 2P vs. No-2P Analysis

An important component of this project is the evaluation of ASCAT under two different configurations.

### ASCAT without 2P inputs

In the automatic configuration, ASCAT estimates tumor purity and ploidy without externally supplied values.

```text
Tumor / Normal Sequencing
           |
           v
   ASCAT WES Processing
           |
           v
   Automatic Model Fitting
           |
           v
   Estimated Purity + Ploidy
           |
           v
   Allele-Specific Copy Number
```

This configuration provides a baseline for comparison with other independent CNV callers.

### ASCAT with 2P inputs

The alternative configuration supplies both tumor purity and ploidy values to the configured ASCAT analysis.

```text
Tumor / Normal Sequencing
           |
           v
    Supplied Purity + Ploidy
           |
           v
      ASCAT Processing
           |
           v
   Copy-Number Model Fitting
           |
           v
   Allele-Specific Copy Number
```

The existing Sarek launcher accepts:

```python
ascat_purity = None
ascat_ploidy = None
```

When both parameters are absent, automatic fitting is requested.

When both are provided, the configured ASCAT invocation receives the supplied values.

The exact effect of these parameters must be verified against the invoked ASCAT version and runtime logs.

### Comparison questions

The analysis investigates:

- Whether supplied 2P values change inferred copy-number profiles.
- Whether 2P inputs improve fitting stability or convergence.
- Whether chromosome-arm CNV classifications differ.
- Whether focal amplification/deletion calls change.
- Whether supplied parameters improve agreement with external reports.
- Whether any improvement reflects genuine model stability or bias toward the source of the supplied estimates.

For valid comparisons, all other analysis parameters should remain unchanged.

**Important:** Externally supplied purity/ploidy values are not automatically considered ground truth.

## FACETS Analysis

FACETS provides an independent approach for estimating allele-specific copy number, tumor purity, and ploidy.

The intended analysis includes:

1. Read allele counts from matched tumor/normal sequencing data.
2. Generate tumor–normal allelic count information.
3. Apply GC and coverage-related normalization.
4. Segment log-ratio and allelic imbalance signals.
5. Estimate tumor purity and ploidy.
6. Derive allele-specific copy-number states.
7. Compare resulting CNV profiles with ASCAT, Sequenza, PURPLE, and BostonGene.

### Key outputs

- Tumor purity
- Tumor ploidy
- Total copy number
- Minor allele copy number
- Allelic imbalance
- Loss of heterozygosity
- Genomic CNV segments

The exact FACETS command and output schema should be documented alongside the validated implementation.

## PURPLE Direct Pipeline

The PURPLE branch uses the Hartwig Medical Foundation tools directly, without running the full nf-core/oncoanalyser workflow.

### Rationale

An earlier version used:

```text
nf-core/oncoanalyser 2.3.0
```

The full targeted workflow involved additional processes including:

- REDUX
- SAGE
- PAVE
- ESVEE
- AMBER
- COBALT
- PURPLE

These modules provide additional read processing, small-variant and structural-variant evidence, but increase computational time and intermediate storage.

For the purity/ploidy/CNV benchmark, a streamlined branch was introduced:

```text
Existing Sarek CRAM
        |
        v
       AMBER
        |
        v
       COBALT
        |
        v
       PURPLE
```

In the implemented sequential runner, AMBER and COBALT execute consecutively. Conceptually, both provide inputs to PURPLE.

### Tool versions

| Tool | Version |
|---|---|
| AMBER | 4.2 |
| COBALT | 2.2 |
| PURPLE | 4.3 |

All three tools run in Docker containers.

### AMBER

AMBER calculates B-allele frequencies using matched tumor and normal sequencing data.

Main functions:

- Identify informative heterozygous germline sites.
- Measure allele balance in the tumor.
- Generate BAF profiles.
- Identify regions with allelic imbalance.
- Provide allele-specific evidence for PURPLE.

Typical output:

```text
<TUMOR_SAMPLE>.amber.baf.tsv.gz
```

### COBALT

COBALT generates normalized read-depth ratios.

Main functions:

- Compare tumor and normal sequencing depth.
- Apply GC-related normalization.
- Use target-region normalization where configured.
- Generate copy-number ratio information.
- Provide coverage evidence to PURPLE.

Typical output:

```text
<TUMOR_SAMPLE>.cobalt.ratio.tsv.gz
```

### PURPLE

PURPLE integrates AMBER and COBALT results to estimate:

- Tumor purity
- Tumor ploidy
- Total copy number
- Allele-specific copy number
- Somatic CNV segments
- Gene-level copy number
- Chromosome-arm copy number

Somatic SNV/indel and structural-variant information can provide additional evidence. The direct workflow does not assume that results without those inputs will be identical to a full Oncoanalyser analysis.

## PURPLE Batch Orchestration

The 20-patient direct PURPLE runner is:

```text
run_purple_direct_20.py
```

The script performs:

1. Input validation.
2. CRAM and CRAI validation.
3. Reference resource validation.
4. Docker image validation.
5. Sequential execution of 20 patients.
6. AMBER, COBALT, and PURPLE processing.
7. Per-patient and per-stage logging.
8. Failure detection.
9. Step-level restart support.

### Resource configuration

| Resource | Configuration |
|---|---|
| Patient execution | Sequential |
| Logical CPU budget | Up to 40 |
| Docker memory limit | 80 GB |
| Reference genome | GRCh38 |
| Execution environment | Docker |
| Failure handling | Stop on failed step |
| Resume behavior | Reuse validated successful stages |

A configured 40-thread maximum does not guarantee all tools will continuously utilize 40 logical CPUs.

### Run preflight

```bash
BASE=/data4/local-bioinformatics/PURPLE_Michael_2.3

python3 "$BASE/run_purple_direct_20.py" \
    --threads 40 \
    --preflight
```

Preflight verifies the availability of expected input files, references, and Docker images.

It does not guarantee scientific validity or successful completion of the entire workflow.

### Start the 20-patient batch

```bash
BASE=/data4/local-bioinformatics/PURPLE_Michael_2.3
LOGDIR="$BASE/logs/PURPLE_direct_batch"

mkdir -p "$LOGDIR"

nohup python3 -u "$BASE/run_purple_direct_20.py" \
    --threads 40 \
    > "$LOGDIR/master.log" 2>&1 \
    < /dev/null &

echo "PURPLE DIRECT PID: $!"
```

## Chromosome-Arm CNV Analysis

Chromosome-arm-level gains and losses are evaluated independently of gene-level events.

An exploratory project-specific classification rule is:

```text
Minimum altered genomic span: 20 Mb
Minimum chromosome-arm coverage: 70%
```

A chromosome arm may be classified as altered when sufficiently large and consistently supported copy-number segments cover the defined arm fraction.

This is a project-specific evaluation rule, not a claim about the internal thresholds used by BostonGene or the individual CNV callers.

### Example

```text
Chromosome 7q
  |
  +-- Altered genomic span >= 20 Mb
  |
  +-- Arm coverage >= 70%
  |
  +-- Copy-number state indicates gain
  |
  v
Chromosome 7q Gain
```

Chromosome-arm calls require careful consideration of:

- Ploidy baseline
- Segment boundaries
- Chromosome length
- Cytoband definitions
- WES target coverage
- Low-purity segmentation artifacts
- Sex chromosome handling

## Gene-Level CNV Analysis

Gene-level analysis evaluates copy-number states in clinically relevant genes.

Examples include:

- Oncogene amplification
- Tumor suppressor deletion
- Homozygous deletion
- Copy-number gain
- Copy-number loss
- Copy-neutral LOH

Gene-level events and chromosome-arm events must be analyzed separately.

A focal event affecting an oncogene should not automatically be interpreted as an entire chromosome-arm gain.

Similarly, a chromosome-arm loss does not necessarily imply homozygous deletion of every gene on that arm.

### Ploidy-aware interpretation

Absolute copy-number thresholds should be interpreted with respect to estimated tumor ploidy.

For example, total CN = 3 can have a different biological interpretation in a near-diploid tumor versus a highly aneuploid tumor.

Therefore, standardized output should retain:

```text
Tumor Purity
Tumor Ploidy
Total Copy Number
Major Copy Number
Minor Copy Number
CNV Classification
```

## BostonGene Clinical Report Comparison

A major objective is to assess concordance between computational CNV estimates and clinically reported findings.

### Comparison categories

The analysis focuses on:

1. Tumor purity
2. Tumor ploidy
3. Chromosome-arm gains
4. Chromosome-arm losses
5. Gene amplifications
6. Gene deletions
7. Homozygous deletions
8. Clinically relevant CNV events

### Comparison approach

For each patient:

```text
ASCAT Results
FACETS Results
Sequenza Results
PURPLE Results
       |
       v
Standardized CNV Table
       |
       v
BostonGene Clinical Report
       |
       v
Concordance Analysis
```

### Concordance classifications

Recommended comparison labels:

| Classification | Definition |
|---|---|
| Concordant | Computational and BG findings agree |
| Partially concordant | Same general event, different boundaries or amplitude |
| Discordant | Computational and BG findings disagree |
| Not assessed | Required evidence is unavailable |
| Not reported by BG | Computational event absent from the reported clinical findings |

**Not reported by BostonGene does not mean biologically absent.**

Clinical reports generally contain selected reportable findings rather than every computationally detectable genomic event.

### Chromosome-arm event comparison

For example, if a BostonGene report contains:

```text
7 chromosome-arm gains
10 chromosome-arm losses
```

The corresponding output of each caller must be filtered using a consistent evaluation rule before comparing event counts.

Differences may reflect:

- Distinct segmentation algorithms
- Different thresholds
- Tumor ploidy assumptions
- Capture-panel coverage
- Low tumor purity
- Reporting criteria

## Quality Control

The project applies tool-specific and cross-tool quality checks.

### Major QC considerations

| Issue | Potential impact |
|---|---|
| Low tumor purity | Unstable purity/ploidy estimation |
| Low sequencing coverage | Unreliable allele frequencies and CNV ratios |
| WES capture bias | Distorted copy-number profiles |
| Incorrect GC normalization | Artificial CNV signal |
| Ploidy ambiguity | Alternative valid model solutions |
| Tumor heterogeneity | Complex or subclonal copy-number states |
| Whole-genome duplication | Changes gain/loss interpretation |
| Genome build mismatch | Incorrect segment and gene coordinates |
| Missing reference resources | Incomplete or failed analysis |
| Caller-specific filtering | Differences in final reportable events |

### Low-purity example

An earlier full-Oncoanalyser PURPLE analysis for CS-26-0073 reported:

```text
Purity: 0.0800
Ploidy: 2.0000
Status: NO_TUMOR
```

This result should be treated as a low-confidence tumor-detection outcome rather than a validated 8% purity measurement.

The direct PURPLE run must be evaluated separately.

## Runtime and Computational Resources

This project aims to minimize unnecessary recomputation.

### Resource strategy

- Reuse Sarek tumor/normal CRAM.
- Avoid repeated FASTQ alignment.
- Run independent CNV callers using shared upstream data.
- Use multi-threading where supported.
- Keep patient execution sequential where required.
- Track CPU and memory utilization.
- Preserve per-patient log files.
- Enable restart from completed stages.

### Direct PURPLE configuration

```text
Maximum logical CPUs: 40
Docker memory limit: 80 GB
Execution: Sequential patients
Reference genome: GRCh38
Input: Tumor + Normal CRAM
```

Actual CPU utilization depends on each tool's implementation and workload.

### Storage considerations

Intermediate BAM/CRAM files and whole-exome reference data can require substantial disk space.

The shared `/data4` storage volume was approximately 98% occupied during the initial October 2026 runs.

The pipeline should not automatically delete shared Sarek working data or original patient files.
